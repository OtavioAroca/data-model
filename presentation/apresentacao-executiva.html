Forma de ModelarTrês eixos de classificação, independentes entre si

Cada produto de dados do domínio Cartão é classificado ao mesmo tempo por três lentes diferentes — a que negócio ele pertence, em que estágio de processamento está, e para quem foi moldado. Nenhuma das três decide as outras duas.

Domain-Driven Design (DDD)

Organiza o domínio em bounded contexts (15 subdomínios do Cartão) e classifica cada um por importância estratégica: Core (diferencial competitivo), Support (necessário, não diferencial) ou Generic (solução de mercado).

Camada Medalhão

Estrutura o data lake por estágio de processamento: Bronze (bruto), Silver (limpo — com a nuance L1 histórico / L2 estado atual) e Gold (pronto para consumo).

Core / Integration / Analytics

Classifica cada produto de dados pelo escopo: Core (1 bounded context), Integration (cruza ≥2 contextos) ou Analytics (moldado para um caso de uso final).

Atenção: "Core" significa três coisas diferentes aqui A mesma palavra aparece nos três eixos, com significados distintos — evita confusão saber qual está em jogo:

Os 15 Subdomínios do Domínio Cartão

Cada card é um bounded context: o que ele resolve, quem alimenta, e quais camadas de produto de dados (Core/Integration/Analytics) já têm produto proposto no catálogo.

BenefíciosPor que modelar dessa forma

Cada decisão de modelagem existe para resolver um problema concreto de custo, velocidade ou alinhamento com o negócio — não é estrutura pela estrutura.

Alinhamento com o negócio

Cada bounded context tem dono, linguagem própria e fronteira de responsabilidade claras — a estrutura técnica espelha a estrutura organizacional, em vez de competir com ela.

Silver L1 e L2 não são redundância

Manter histórico completo (L1) separado do estado atual materializado (L2) evita recalcular a regra de precedência de negócio a cada leitura. Auditoria lê L1; operação lê L2 — cada público paga só pelo custo que precisa.

Integration evita integrações N×M

Sem um produto Integration que padroniza schema entre bounded contexts, cada consumidor teria que cruzar os mesmos contextos de forma independente — N consumidores × M fontes. Um produto Integration resolve isso uma vez.

Analytics em português, Core/Integration em inglês

Quem consome Analytics é risco, marketing, financeiro — não engenharia. Nomear em português remove uma tradução mental a cada consulta, sem abrir mão de convenção técnica onde o público é técnico.

Catálogo reduz descoberta ad-hoc

Produto de dados = dono, contrato e consumidores documentados no catálogo — não uma tabela órfã que alguém precisa perguntar no chat quem mantém.

Escala subdomínio por subdomínio

Cada bounded context tem sua própria pasta de catálogo. Um novo time de domínio se integra adicionando a sua, sem reescrever o que já existe para os outros 14.

Estudo de CasoCompras / Autorização

Subdomínio Core escolhido como piloto por ser o mais crítico do fluxo de cartão: autoriza e captura toda transação, incluindo o parcelamento decidido no ato da compra.

Pipeline: Bronze → Silver L1/L2 → Gold

O piloto tem dois rails (crédito e débito), cada um com 5 tópicos Bronze de status (approved/denied/cancelled/clearing/processed) → Silver L1 (histórico) → Silver L2 (estado atual). O rail de crédito ainda tem duas tabelas Core adicionais para o detalhamento de parcelas (credit_transaction, credit_transaction_type). Os dois rails convergem em gold.integration__purchase_journey, que junto dos produtos Analytics soma as tabelas Gold. Exemplo do rail de crédito:

bronze.purchases__credit_approved → silver_l1.purchases__credit_purchase
(histórico, N por compra) → silver_l2.purchases__credit_purchase
(estado atual, 1 por compra) → gold.integration__purchase_journey
