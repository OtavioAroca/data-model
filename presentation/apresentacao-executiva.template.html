O problema

Hoje não existe forma sistemática de saber, para uma tabela qualquer do parque de dados, quem é o dono, o que ela representa ou se pode ser usada com confiança numa decisão — descobrir isso depende de perguntar a quem talvez já não esteja mais no time.

A proposta

Uma forma de catalogar produtos de dados — dono, contrato, linhagem — subdomínio por subdomínio. Para testar se funciona num caso real, desenhamos em detalhe como Compras/Autorização ficaria: . Nada disso está construído ainda — é o plano de referência a validar antes de implementar.

A decisão necessária

Aprovar a construção real deste primeiro piloto, com apoio do time de Compras/Autorização para validar o desenho contra os sistemas de origem — e decidir qual subdomínio entra em seguida.

Forma de ModelarDois eixos de classificação, independentes entre si

Cada produto de dados do domínio Cartão é classificado ao mesmo tempo por duas lentes diferentes — em que estágio de processamento está, e para quem foi moldado. Nenhuma das duas decide a outra.

Camada Medalhão

Estrutura o data lake por estágio de processamento: Bronze (bruto), Silver (limpo — com a nuance L1 histórico / L2 estado atual) e Gold (pronto para consumo).

Core / Integration / Analytics

Classifica cada produto de dados pelo escopo: Core (1 subdomínio), Integration (cruza ≥2 subdomínios) ou Analytics (moldado para um caso de uso final).

Os 15 Subdomínios do Domínio Cartão

Cada card é um subdomínio do negócio: o que ele resolve, quem alimenta, e quais camadas de produto de dados (Core/Integration/Analytics) já têm produto proposto no catálogo.

BenefíciosPor que modelar dessa forma

Cada decisão de modelagem existe para resolver um problema concreto de custo, velocidade ou alinhamento com o negócio — não é estrutura pela estrutura.

Decisão não trava esperando alguém lembrar

Cada subdomínio tem dono e fronteira de responsabilidade claros — a estrutura dos dados espelha quem no negócio responde por aquilo, em vez de exigir que alguém pergunte em algum chat quem sabe do assunto.

Auditoria e operação deixam de competir pelo mesmo dado

Histórico completo (para quem precisa reconstituir o passado, como auditoria) fica separado do estado atual (para quem opera no dia a dia) — cada público lê a versão certa para o que precisa, sem recalcular nada nem esperar o outro.

Evita retrabalho duplicado entre times

Sem um produto padronizado que cruza dois subdomínios, cada time que precisa da mesma combinação de dados faz esse cruzamento sozinho — com risco real de dois times chegarem a números diferentes para a mesma pergunta. Um produto compartilhado resolve isso uma vez, para todos.

Quem decide não perde tempo traduzindo

Risco, marketing e financeiro leem métricas de negócio em português, sem tradução mental a cada consulta — menos chance de erro de interpretação numa decisão que envolve dinheiro.

Investimento é incremental, não tudo-ou-nada

Cada subdomínio é independente no catálogo. Aprovar o próximo não exige reabrir ou re-validar os que já foram definidos — o risco de cada rodada de investimento é isolado.

Reduz risco de auditoria e compliance

Sem contrato e linhagem documentados, uma tabela usada num relatório para o regulador não tem como provar de onde veio o dado — a defesa depende de investigação manual sob pressão, não de rastreabilidade automática.

Piloto PropostoCompras / Autorização

Subdomínio Core escolhido para o desenho de referência por ser o mais crítico do fluxo de cartão: autoriza e captura toda transação, incluindo o parcelamento decidido no ato da compra.

Nada disto está implementado O que segue é o desenho detalhado de como este subdomínio ficaria se construído seguindo esta metodologia — tabelas, produtos e linhagem propostos, não um sistema em produção. Serve para provar que o desenho é aplicável a um caso real antes de pedir aprovação para construí-lo de fato.

Pipeline proposto: Bronze → Silver L1/L2 → Gold

O desenho propõe dois rails (crédito e débito), cada um com 5 tópicos Bronze de status (approved/denied/cancelled/clearing/processed) → Silver L1 (histórico) → Silver L2 (estado atual). O rail de crédito ainda teria duas tabelas Core adicionais para o detalhamento de parcelas (credit_transaction, credit_transaction_type). Os dois rails convergiriam em gold.integration__purchase_journey, que junto dos produtos Analytics soma as tabelas Gold propostas.

Visão de produtos: o que depende do quê

O filtro "Produto de dados" no mapa acima não é só uma lista — desmarcar um produto sinaliza em vermelho, em cascata via linhagem, tudo que depende dele (tabelas e setas), sem esconder nada do contexto. É a pergunta que toda mudança de negócio levanta: "se pararmos de fazer X, o que é afetado?"

Exemplo real do piloto: e se saíssemos de débito? Desmarcando core_debit_purchase no filtro acima, a cascata acende em vermelho 18 das 29 tabelas — não só as 7 do rail de débito, mas 12 dos 15 produtos do piloto: o Integration (gold.integration__purchase_journey) e todos os 10 produtos Analytics, porque vários leem direto de tabelas Silver de débito, sem passar pelo Integration. Só os 3 produtos exclusivos de crédito ficam de fora. Descontinuar débito não seria isolado — exigiria revisar quase todo o piloto antes de desligar qualquer tabela. Essa resposta só existe porque a linhagem está documentada; para os outros 14 subdomínios, essa mesma pergunta não tem resposta hoje.
